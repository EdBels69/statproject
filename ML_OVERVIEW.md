#### Layout: почему пусто по бокам и что с этим делать

**Наблюдение:** на широких экранах интерфейс выглядит как «статья по центру», вокруг — большие мёртвые поля.

**Экспертная оценка текущего экрана (на примере StatWiki):**
- Сильные стороны: хорошая иерархия, спокойный фон, аккуратные карточки, читабельный ритм.
- Слабые стороны: лишнее сужение рабочей области, боковые поля не несут функции, плотность информации ниже возможной.
- Риск: в продукте‑инструменте пользователь платит “временем мыши” за каждый лишний скролл/клик из‑за узкого каркаса.

**Причина (текущая реализация):** ширина ограничивается дважды.
- Глобально: `MainLayout` заворачивает любой экран в контейнер `max-w-[1400px]`.
- Локально: отдельные страницы (например, `StatWiki`) ещё раз ограничивают контент (`max-w-5xl`).

**Побочный эффект:** даже при 1920px ширины рабочая зона для «ПО‑инструмента» становится узкой, а боковые поля ничего не делают.

**Оптимальные решения (паттерны для аналитического ПО):**

1) **Стратегия контейнеров (3 режима)**
- `reading`: максимум 980–1100px (документация/вики, длинные тексты).
- `workbench`: максимум 1440–1680px (мастер протокола, конфиг тестов, каталоги).
- `canvas`: 100% ширины (графики/таблицы, heatmap, ROC, корр.матрицы).

2) **Один источник правды для ширины**
- Контейнер задаётся на уровне layout (обёртки), а страницы не ставят `max-w-*` внутри.
- Вариант задаётся маршрутом/пропом (`layoutVariant`) и переключается без копипаста.

3) **Правые/левые rails вместо пустоты**
- Левый rail: оглавление/поиск/фильтры (особенно для вики и каталогов методов).
- Правый rail: контекстный инспектор (предпосылки, что репортить, pitfalls, быстрые примеры, ссылки на связанные термины).
- Rails — `sticky`, на малых экранах схлопываются в drawer.

4) **Трёхпанельный grid как базовый рабочий паттерн**
- `320px | minmax(0, 1fr) | 360px` для “list → details → inspector”.
- Плюс возможность скрыть правую панель (focus‑mode) и/или сделать панели ресайзабельными.

5) **Правило длины строки (читаемость без «пустыни»)**
- Для текстов держать 70–85 символов/строка, но это не значит сужать весь интерфейс.
- Решение: ограничивать только текстовые блоки (описания), а не каркас страницы.

**Практическая цель для продукта:** на широких экранах боковые поля должны либо исчезать (расширяем workbench/canvas), либо становиться функциональными (rails). В текущем состоянии — это потеря площади и скорости работы.

### Этап 4 — AI‑интерпретация и ассистент (P1)

**Цели:** дать пользователю объяснения, не требующие статистической подготовки.

**Задачи:**
- Реализовать генерацию интерпретаций на основе шаблонов.
- Добавить AI‑консультанта для «почему этот тест».
- Сформировать публикационное заключение (Results paragraph).

#### Декомпозиция Этапа 4 (чтобы это стало продуктовой фичей, а не “текстом из воздуха”)

1) **Provenance (обязательная прослеживаемость источника)**
- Каждая AI‑рекомендация/интерпретация должна содержать: *источник*, *правило/скрипт*, *входные факты*, *ограничения*.
- В UI выводить «Почему так?» как список проверок: тип переменной, структура групп, предпосылки, альтернатива при нарушениях.

2) **Скриптовый ассистент протокола (без магии)**
- Вход: профиль колонок (тип/роль/пропуски/выбросы), цель исследования, структура (independent/paired), n, число групп.
- Выход: список шагов протокола: чистка → предпосылки → основной тест → post‑hoc/коррекции → effect size + CI → графики.
- Правило: ассистент не «придумывает» тесты; он выбирает из доступного списка движка и объясняет выбор.

3) **Единый формат карточки рекомендации**
- `title`, `what_to_do`, `why`, `assumptions`, `fallback`, `reporting`, `confidence`, `links_to_wiki`.
- Обязательный минимум: `what_to_do` + `why` + `fallback`.

4) **Контроль качества текста**
- Тон: нейтральный, клинический; без категоричности.
- Шаблоны должны покрывать: значимо/незначимо, пограничные p, малые выборки, большие n (практическая значимость).

5) **i18n как часть фичи**
- Любой AI‑текст: либо локализованный шаблон, либо строго размеченный словарь терминов (RU/EN), без “сырого” ключа.

**Критерии приёмки:**
- Генерация интерпретаций на 100% методов.
- Тексты единообразны и корректны по APA‑логике.
- Любая рекомендация в UI имеет «почему» и «что делать дальше».
