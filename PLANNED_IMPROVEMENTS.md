# План доработок StatProject (черновик)

Цель: довести продукт до состояния, где данные всегда видны, действия предсказуемы, ошибки понятны, а интерфейс ощущается «редактором» (не формой) — при этом без деградации производительности на больших таблицах.

## 1) Таблица данных (UI/UX)

### 1.1. Виртуализация и производительность
- Что: гарантировать стабильную работу на 100+ колонок и десятках тысяч строк.
- Как: переключить таблицу данных на режим виртуализации (строки и/или колонки), лимитировать рендер ячеек, включить lazy chunks там, где это окупается.
- Зачем: AG Grid уже тяжёлый по бандлу; рост объёма данных быстро делает интерфейс «тяжёлым» по вводу/скроллу.

### 1.2. Умная автоширина / фиксированная первая колонка
- Что: комфортное чтение при 119 колонках: фиксировать индекс/ключевые колонки, сделать быстрые пресеты ширины.
- Как: пресеты `compact / readable / wide`, pinned-колонки, кнопка “подогнать видимые”.
- Зачем: уменьшает когнитивную нагрузку и время поиска нужного столбца.

### 1.3. Пустые состояния и диагностика прямо в гриде
- Что: если `head` пустой/не пришёл — показывать понятное “нет строк для отображения” + причину.
- Как: пустой state внутри области грида, отображение `row_count`, `page`, `total_pages`, и “перезагрузить”.
- Зачем: сейчас «пусто» визуально не отличимо от “не отрендерилось”.

## 2) Лист переменных (mapping)

### 2.1. Версионирование сопоставления (уже начато)
- Что: история изменений mapping с быстрым откатом.
- Как: хранить бэкапы по времени (уже: `processed/backups/variable_mapping.<ts>.json`), добавить endpoint “список бэкапов / восстановить конкретный”.
- Зачем: безопасная работа с массовыми правками; можно экспериментировать.

### 2.2. Массовые операции, которые реально нужны
- Что: bulk-назначение роли/типа/подгруппы/точки времени с понятной областью применения.
- Как: применять к “всем отфильтрованным”, показывать счётчик затронутых, делать undo.
- Зачем: ускоряет разметку для отчётов и анализа, снижает риск ошибочной правки.

### 2.3. Автоподсказки по ролям
- Что: предлагать роль (ID/Группа/Исход/Ковариата) на основе имени и типа.
- Как: эвристики по ключевым словам + статистика уникальности/пропусков.
- Зачем: меньше ручного труда и меньше ошибок по невнимательности.

## 3) Листы Excel и выбор источника данных

### 3.1. Явная модель «активный лист»
- Что: пользователь всегда видит, какой лист Excel сейчас активен.
- Как: показывать текущий лист в заголовке, и сохранять выбор листа на датасет.
- Зачем: в много-листовых файлах иначе легко «потеряться».

### 3.2. Выбор строки заголовков
- Что: контролируемая смена header row без сюрпризов.
- Как: UI-параметр “строка заголовков” + предпросмотр первых 10 строк.
- Зачем: реальные Excel часто имеют «шапку» не на первой строке.

## 4) Надёжность API и корректность действий

### 4.1. Проверить DELETE датасета в dev
- Что: устранить 405 Method Not Allowed на удаление в локальном окружении.
- Как: сверить маршруты, префиксы и прокси, убедиться что `DELETE /api/v1/datasets/{id}` указывает на нужный роутер.
- Зачем: удаление — базовая операция, без неё копится мусор в workspace.

### 4.2. Стабильные ошибки для фронта
- Что: унифицировать формат ошибок (код/сообщение/контекст).
- Как: общий error handler на бэке, на фронте — единый парсер `detail`.
- Зачем: меньше “непонятных” падений, проще поддержка.

## 5) Аналитика/протоколы

### 5.1. Прозрачность предпосылок
- Что: выводить результаты проверок предпосылок (нормальность, дисперсии) как «карточки решения».
- Как: сохранять результаты проверок рядом с run, показывать что было проверено и что выбрано.
- Зачем: доверие к результатам и воспроизводимость.

### 5.2. Репорты: связь с mapping
- Что: отчёты должны использовать display_name/роль/группировку из листа переменных.
- Как: на этапе генерации отчёта подтягивать mapping и применять к таблицам/графикам.
- Зачем: отчёт становится “человеческим”, без сырой техничной нотации.

## 6) Стабилизация UI и качество

### 6.1. Е2Е на ключевые сценарии
- Что: тесты на загрузку Excel → просмотр таблицы → разметка переменных → экспорт.
- Как: Playwright сценарии + фикстуры демо-датасета.
- Зачем: защитить от регрессий, вроде «таблица пустая».

### 6.2. Контроль размера бандла
- Что: держать чанк с гридом отдельно и не раздувать главный.
- Как: manualChunks/динамические импорты для тяжёлых экранов.
- Зачем: быстрый первый рендер и ощущение “легкости”.
