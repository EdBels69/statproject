# План доработки Auto‑Design под широкие таблицы (10k×10k) и слабые модели

## Цель

Сделать Auto‑Design и интерпретации устойчивыми к широким данным (тысячи–десятки тысяч переменных), чтобы даже слабая модель (уровня GLM‑4.7 Flash / «cheap+fast») могла давать экспертный, осмысленный результат без попыток «проглотить» гигантские таблицы.

Ключевой принцип: LLM не должен видеть огромные матрицы; он должен получать компактные, вычисленные детерминированно «дайджесты», а затем принимать решения и формулировать выводы.

## Что сейчас смешано

- LLM‑планирование (auto‑design) и вычисления масштаба 10k×10k нельзя решать одним промптом.
- «Слабая модель» ломается не потому, что она плохая, а потому что ей дают задачу с неправильной формой входа: слишком большой объём, слишком слабая структура, нет бюджето‑ограничений.

## Целевое разбиение на контуры

1) Deterministic Condenser (не‑LLM)
- На вход: df + scan/meta.
- На выход: компактные JSON‑дайджесты (не более десятков KB).

2) Planner (LLM)
- На вход: meta + дайджесты + budgets/preferences.
- На выход: протокол (JSON) с жёсткими лимитами.

3) Executor (не‑LLM)
- На вход: протокол.
- На выход: результаты шагов.

4) Explainer (LLM)
- На вход: по одному шагу: маленький срез результата (top‑K строк/контрастов/эффектов).
- На выход: 3–6 предложений интерпретации.

## Практики под GLM‑4.7 Flash / дешёвые модели

### 1) Budget‑first протокол

- Всегда передавать в prompt лимиты: max_steps, max_corr_vars, max_outcomes.
- Вынести «самопроверку» в текст промпта: модель обязана валидировать ограничения до ответа.
- Температура ниже (0.2–0.3), ограничение max_tokens (2–3k), строго JSON.

### 2) Column‑Index (Map‑Reduce) для широких признаков

Когда переменных много (10k+), LLM физически не должен видеть полный список разом. Делать:

- Map: разбить список колонок на чанки (например 200–600 имён на чанк), запросить от модели:
  - список кандидатов outcome/group/time/subject по именам
  - короткие причины выбора
  - «сигнальные» регулярки/паттерны
  - предложения по «семействам эндпоинтов» (baseline/endpoint, *_v1..vN)
  - предложения по UI‑группам переменных (rule + 10–30 примеров)

- Reduce: объединить кандидатов/правила, дедуплицировать, ранжировать, собрать единый column_index.json.

Важное: модель в map‑шаге видит только имена/типы/пропуски и лёгкие Python‑сигналы (см. раздел «Прескан»), но не видит больших таблиц значений.

### 3) Строгое сжатие результатов и отчёта при all‑on‑all

All‑on‑all можно считать Python‑скриптами/движком, но нельзя:
- передавать в LLM матрицы 10k×10k,
- пытаться визуализировать полную матрицу человеку.

Вместо этого — компактные форматы вывода (артефакты) и дайджесты для LLM:

- Correlation output (для numeric):
  - edges_topk: top‑K пар по |r| (K=1k–50k) + метрики (r, p/p_adj опционально)
  - edges_threshold: «разреженный граф» для |r|>=t (t настраиваемый)
  - per_var_degree: топ‑N переменных по числу сильных связей (N=200–1000)
  - blocks: блочная структура по семействам/кластерам (cluster_id → список переменных)
  - representatives: по одному представителю на блок/кластер (для heatmap 100–300)

- Massive group comparisons output (для group):
  - per_variable: минимальный результат по каждой переменной (method_used, p, p_adj, effect_size, n)
  - ranked_views: top‑N по p_adj и отдельно top‑N по |effect|
  - family_summary: суммарная статистика по семействам эндпоинтов (сколько сигналов прошло FDR)
  - stratified: те же представления по подгруппам, но с ограничением числа strata и агрегацией

- Missingness digest:
  - топ столбцов по пропускам
  - «блоки» пропусков (если выявляются)

## Граница «человек осилит» vs «масштабное» (рекомендуемая шкала)

Граница на практике определяется не только вычислениями, а тем, что можно:
- хранить,
- отрендерить,
- интерпретировать без самообмана.

### Корреляции (p переменных → p(p−1)/2 пар)

- p ≤ 200 (≈20k пар): «человек осилит» классическую heatmap/кластеризацию и читать отчёт.
- p 200–500 (≈20k–125k пар): ещё ок, но уже нужен интерактив/фильтры.
- p 500–2k (≈125k–2M пар): полный список пар бессмысленен; нужны top‑K, пороги, кластера, представители.
- p 2k–10k (≈2M–50M пар): только разреженные представления (top‑K/threshold graph/блоки) + оффлайн‑артефакты. Полная матрица — только как бинарный артефакт/индекс, не для UI.

Практическая UI‑граница для heatmap: 150–300 переменных (выше — нечитаемо и тяжело рендерить).

### Массовые сравнения (m таргетов × strata)

- m ≤ 200 и strata ≤ 3: можно показывать таблицу на экране и читать выводы.
- m 200–2k: нужен ранжированный список + фильтры + family grouping.
- m 2k–10k+: UI должен быть поиском/срезами, а отчёт — агрегатами + top‑N.

## Взаимодействие при дизайне: как «утвердить» множественные сравнения и strata

Поскольку LLM видит только метаданные, дизайн должен быть интерактивным контрактом между системой и исследователем.

### 1) Стадия Draft (LLM)

- Предложить 2–4 кандидата дизайна.
- Предложить разбиение переменных на семейства/группы по имени.
- Предложить первичные/вторичные семейства эндпоинтов (по имени) с уровнем уверенности.

### 2) Стадия Confirmation (исследователь)

Нужно утвердить явно:
- Основной group_column.
- Список strata (подгрупп) и их приоритет (обязательные/опциональные).
- Семейства эндпоинтов и «что считать первичным».
- Политику множественных сравнений:
  - FDR на всём массиве vs FDR по семействам vs иерархия (primary→secondary).
- Порог отчёта: top‑N, пороги |effect|, пороги |r|, min_n.

### 3) Стадия Execution (Python)

- Тотальные расчёты выполняются чанками и сохраняют артефакты.
- UI читает индекс‑файлы/ранжированные представления, а не «сырую матрицу».

### 4) Стадия Interpretation (LLM)

- LLM интерпретирует только дайджесты: агрегаты, top‑N, family summaries.

## Прескан (Python) чтобы различать ID, time и «ложные числовые исходы»

Одних имён столбцов недостаточно. Нужен быстрый прескан без тяжёлых расчётов:

- cardinality_ratio = nunique / n_rows
- is_monotonic (для числовых) + шаги (подозрение на ID/таймстамп)
- duplicate_rate (для потенциальных ID)
- simple_type_hints: can_parse_datetime, can_parse_numeric
- value_length_stats (для object): средняя длина, доля цифр, доля букв
- missing_rate

Выход прескана должен попадать в column_index.json и использоваться LLM при выборе group/time/subject и при исключении «технических» колонок из endpoints.

### 4) Двухступенчатая интерпретация

Для больших результатов:

1) Step summarizer (не‑LLM) сворачивает сырьё до JSON: только ключевые цифры, top‑K контрастов, признаки значимости.
2) Explainer (LLM) пишет краткую интерпретацию по этому JSON.

Такую схему можно применять к:
- post‑hoc сравнениям (оставлять только top‑K значимых пар)
- регрессиям (оставлять только top‑K коэффициентов по |t|/|z|)
- смешанным моделям (оставлять interaction p, оценённые средние по ключевым визитам)

## Чанкование: что именно чанковать

### А) Чанкование признаков (по именам)

- Цель: выбор переменных (outcome/group/time/subject).
- Вход: список {{n,t,u,m}}.
- Выход: кандидаты + ранжирование + причины.

### Б) Чанкование результатов (после расчёта)

- Цель: интерпретация (interpret_table / interpret_general_summary).
- Вход: дайджест результата с лимитом размера.
- Выход: краткий текст.

### В) Чанкование протокола (при необходимости)

- Цель: слабая модель может «потерять» структуру в длинном JSON.
- Подход: просить генерировать 6–10 шагов за раз и агрегировать, но только если реально нужен длинный протокол.

## Кэш: что кэшировать

Сейчас есть in‑memory LRU‑кэш в llm слое. Для широких данных полезнее дисковый кэш артефактов.

### 1) Кэш дайджестов (обязателен)

- Ключ: dataset_id + hash(scan_report/dtypes/parquet_mtime) + version(condenser).
- Содержимое: condensed_meta.json, variable_candidates.json, correlation_digest.json.
- Размещение: в dataset run/artifacts или отдельной директории внутри dataset.

### 2) Кэш LLM ответов (вторичен)

- Ключ: hash(prompt + normalized_input + model_id + prompt_version).
- Содержимое: raw_text + extracted_json.
- TTL дольше (сутки) для планировщика, короче (10–30 мин) для интерпретаций.

### 3) Кэш «агентных» шагов

- Map‑результаты по чанкам хранить как JSONL (по строке на чанк) и затем редьюсить.
- Это облегчает ретраи и отладку.

## Промежуточные файлы (что и зачем)

Рекомендуемая схема артефактов:

- ai/condensed_meta.json
- ai/variable_candidates.json
- ai/correlation_digest.json
- ai/auto_design_plan.json
- ai/map_chunks_candidates.jsonl

Плюсы:
- воспроизводимость
- возможность повторно использовать дайджесты без LLM
- быстрые ретраи только «упавших» чанков

## Набор ИИ‑агентов (обзор)

### Agent 1 — Column Classifier (Map)

- Вход: чанк колонок {{n,t,u,m}} + короткие правила.
- Выход: кандидаты outcome/group/time/subject + короткие причины.
- Модель: cheap+fast.

### Agent 2 — Candidate Reducer (Reduce)

- Вход: все map‑ответы.
- Выход: финальные топ‑кандидаты (например top 5 на каждую роль) + confidence.
- Модель: cheap+fast или чуть сильнее.

### Agent 3 — Protocol Planner

- Вход: meta + финальные кандидаты + budgets.
- Выход: protocol JSON (resource‑bounded).
- Модель: GLM‑4.7 Flash или эквивалент.

### Agent 4 — Result Digest Builder (не‑LLM)

- Вход: raw результат шага.
- Выход: компактный digest (top‑K, ключевые поля) для LLM.

### Agent 5 — Step Explainer

- Вход: digest одного шага + минимальный контекст (outcome/group/time).
- Выход: 3–6 предложений.
- Модель: cheap+fast.

### Agent 6 — General Summary

- Вход: набор digest по шагам (не все сырые результаты).
- Выход: общий вывод, ограничения, что делать дальше.

## План внедрения (итерации)

### Итерация 1 (быстро, без изменения вычислительного ядра)

- Сделать промпт Auto‑Design «resource‑bounded» с лимитами и самопроверкой.
- Ограничить протокол: меньше шагов, фиксированный max_corr_vars.

### Итерация 2 (сильный прирост качества на широких данных)

- Добавить deterministic condenser и сохранять дайджесты как артефакты.
- Перевести планирование на вход «meta + candidates + digest», а не «всё подряд».

### Итерация 3 (стабильные экспертные интерпретации)

- Встроить digest builder для каждого типа результата (таблица, регрессия, mixed).
- Прокинуть в interpret_table не «таблицу целиком», а digest.

### Итерация 4 (устойчивость/стоимость)

- Ввести JSONL map‑reduce и дисковый кэш.
- Добавить ретраи по чанкам и деградацию: если LLM недоступен — возвращать протокол‑черновик по эвристикам.
