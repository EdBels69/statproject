# AI End-to-End Workflow Plan (Chat -> Design -> Clean -> Analyze -> Report)

Дата: 2026-02-08

## 0) Что именно ты хочешь получить (в одном предложении)

Пользователь пишет подробный запрос в чат; Gemini по этому запросу и по таблице строит дизайн исследования и план анализа (включая тесты, настройки и графики), предлагает его на согласование, затем запускает анализ и выдает:

- единый отчет в `DOCX` и/или `PDF`,
- “таблицу/датасет, по которому реально считали” (analysis dataset),
- прозрачный лог очистки/импутации/фильтрации,
- и при необходимости отдельный режим “сложного data mining” (бутстреп, random forest, кластеризация).

## 1) Почему сейчас ощущение, что “что-то потерялось”

Это не “баг”, а результат того, что система сейчас работает как набор отдельных функций, а не как жестко связанный workflow:

- **Чат → дизайн**: LLM может предложить протокол, но протокол не всегда включает этапы очистки/импутации как обязательный “шаг 0”.
- **Очистка**: очистка частично происходит при ingest (авто-clean/auto-impute), частично есть ручные операции, но это не интегрировано в “выполнить комплексный анализ”.
- **Фиксированный N**: без отдельного “freeze cohort” N плавает, особенно в моделях; это ломает сравнимость и “статьевость”.
- **Сложные методы**: система по умолчанию осторожна (чтобы не делать p-hacking/overfitting и не тратить время), поэтому без явного режима/требований LLM часто предлагает минимально достаточный статистический набор.
- **Репортинг**: отчет может быть “кучей результатов”, если нет строгого контракта на структуру и обязательные артефакты (таблицы/графики/интерпретации/обсуждение).

Вывод: нужен единый контракт и единый pipeline, где каждый этап либо выполнен и зафиксирован, либо анализ не стартует (в “publication mode”).

## 2) Целевой UX: как это должно выглядеть в приложении

### Экранная логика (похожа на Jamovi/JASP, но с AI)

1. **Upload / Dataset**
   - загрузка таблицы,
   - авто-скан качества (пропуски, константы, типы),
   - авто-черновая семантика/роли (outcome/exposure/covariates/time/group).

2. **AI Chat (Research brief)**
   - пользователь описывает задачу “человеческим языком”,
   - Gemini возвращает **структурированный план**:
     - cleaning plan (что делать с пропусками/типами/категориями),
     - design plan (roles, outcome definition, endpoints),
     - protocol (анализы + конфиги),
     - report spec (какие таблицы/графики и как интерпретировать),
     - guardrails (что primary/secondary, что exploratory).

3. **Review & Customize**
   - UI показывает план как “набор карточек шагов”, где у каждого шага:
     - метод, переменные, настройки, ожидаемый вывод,
     - чекбоксы “включить/выключить”,
     - параметры (alpha, коррекции, пост-хоки, биннинг, interaction, ROC и т.д.),
     - привязанные графики (и их пресеты).

4. **Data Cleaning (до анализа)**
   - кнопка “Применить план очистки”:
     - нормализация категорий,
     - конверсия типов,
     - обработка пропусков: drop (если много) vs impute (если мало) по правилам,
     - сохранение `cleaning_log` + возможность отката/версий.

5. **Freeze cohort (фиксированный N)**
   - система предлагает “заморозить когорту” по моделям:
     - `complete_case` или `simple_impute`,
     - строгий режим по моделям (чтобы в логистике/линейке N был одинаковым),
     - fingerprint датасета, чтобы не было “тихого рассинхрона”.

6. **Execute**
   - запуск протокола,
   - сохранение артефактов:
     - `results.json`,
     - `analysis_dataset.xlsx`/`analysis_dataset.parquet`,
     - изображения графиков,
     - report IR (блоки отчета).

7. **Export**
   - “Скачать DOCX”, “Скачать PDF”, “Скачать analysis dataset”.

## 3) Что нужно зафиксировать контрактами (иначе будет хаос)

### 3.1 Контракт “Plan response” (из Gemini)

LLM должен отдавать не “текст”, а JSON-подобную структуру (не обязательно JSON в UI, но структура должна быть однозначна):

- `research_brief`: цель, вопросы, primary outcome, secondary outcomes.
- `dataset_mapping`: какие колонки являются чем (включая правила кодирования исхода).
- `cleaning_plan`: список операций (тип, колонки, параметры).
- `cohort_plan`: правила фиксированного N (mode/enforce/strict + колонки).
- `protocol`: список шагов анализа (method + config + plots + expected tables).
- `report_spec`: структура отчета (sections + per-table/per-figure interpretation requirements).
- `exploratory_plan` (опционально): ML/кластеризация/бутстреп как отдельный режим.

Важно: LLM может предлагать, но не должен “тайно менять выборку” во время исполнения. Для этого нужен freeze cohort артефакт.

### 3.2 Контракт “Run artifacts”

Каждый run обязан сохранить:

- “какие данные использовались”: `analysis_dataset.*`,
- “какие шаги и конфиги”: `protocol.json` (нормализованный),
- “что получилось”: `results.json`,
- “как это показать”: `report IR` (структурированные блоки),
- “какие варнинги/ограничения”: warnings + quality notes.

## 4) Возврат этапа Cleaning: где он должен жить и как работать

Очистка не должна быть “между делом”. В публикационном workflow это отдельный обязательный этап.

### Минимальный набор (P0)

- унификация пропусков (включая `''`, `na`, `null`, `none`),
- нормализация категорий (trim/lower, словари замен),
- приведение типов (числа/даты/категории),
- стратегия пропусков:
  - если пропусков много и переменная не критична: исключить из моделей/таблиц,
  - если переменная критична: имpute (простой или MICE, зависит от режима).

### Версионирование (P0)

- `cleaning_log` + `delta_log`,
- сохранение “до/после” (или снапшоты processed history),
- четкая связь “этот отчет посчитан на версии данных X”.

## 5) Как вернуть “сложный” data mining (и не превратить в мусор)

Ключ: отделить **confirmatory / publication** от **exploratory / mining**.

### Два режима анализа

1. **Publication mode**
   - фиксированная когорта,
   - заранее определенные модели/тесты,
   - строгие проверки качества,
   - отчет с интерпретацией и таблицами/графиками.

2. **Exploratory mining mode**
   - цель: гипотезогенерация и поиск сигналов,
   - методы:
     - random forest / gradient boosting,
     - permutation importance / SHAP (если добавим),
     - кластеризация (k-means/hdbscan) и профили кластеров,
     - bootstrap для устойчивости эффектов,
     - cross-validation для предиктивных метрик (ROC-AUC, PR-AUC).
   - обязательные guardrails:
     - четко маркировать как exploratory,
     - строгий контроль leakage,
     - separate train/test или CV,
     - отчет: “что нашли” + “что надо подтверждать”.

### Практический компромисс

Сложный mining включать не “всегда”, а когда пользователь ставит флажок “Exploratory deep dive” или выбирает “уровень глубины” (Basic / Standard / Deep).

## 6) Почему “комплексный анализ” сейчас не получается автоматически

Если не задать системе явный стандарт, LLM будет оптимизировать на:

- минимальную достаточность,
- безопасность интерпретаций,
- скорость,
- меньший риск сделать неправильно.

Чтобы всегда получался “богатый” результат, надо:

- заранее определить “definition of done” для отчета (обязательные таблицы/графики/интерпретации),
- сделать пресеты протоколов (например “COVID mortality + glycemia”),
- добавить режим глубины (и жёстко требовать дополнительные секции/метрики в Deep).

## 7) План доработки (инженерный, по шагам)

### P0: Связать workflow в одну цепочку (без новых методов)

- Единый структурированный ответ планировщика (design + cleaning + cohort + protocol + report spec).
- UI “Review & Customize” как обязательный шаг перед execute.
- Cleaning stage как отдельная кнопка “Применить план очистки” + логирование.
- Freeze cohort обязателен для “publication mode” (чтобы N фиксировался).
- Export: единый DOCX/PDF + analysis dataset download.

Acceptance criteria:
- из чата можно пройти полный путь до DOCX/PDF,
- отчет содержит оглавление, таблицы, графики и интерпретации “после каждого блока”,
- можно скачать dataset, по которому считали.

### P1: Поднять качество статистики “для статьи”

- Обязательные baseline таблицы по исходу и ключевым экспозициям.
- Регрессионные модели:
  - univariable OR,
  - multivariable logistic regression с наращиванием ковариат,
  - interaction (например glycemia * DM2),
  - ROC/калибровка (если включено).
- Sensitivity analyses:
  - complete-case vs impute,
  - subgroup (без исходного диабета и т.д.).

### P2: Добавить exploratory mining (как отдельный режим)

- ML шаги как явные protocol steps (не “магия”).
- Bootstrap/CV как “wrapper steps” вокруг моделей.
- Авто-генерация “model card” в отчете: данные, метрики, ограничения.

## 8) Аналогии с другими приложениями (для ориентира)

- **Jamovi/JASP/SPSS/Stata/Prism**: сильны в “стандартных статистических кнопках” и воспроизводимости, но без AI-оркестрации.
- **Orange/KNIME/RapidMiner**: сильны в “пайплайнах” и визуальных workflow для data mining.
- **RMarkdown/Quarto/Jupyter**: сильны в “единый отчет + код + данные”, но требуют навыков.

Твой целевой продукт = Jamovi/JASP UX + Orange pipeline строгости + Quarto-style отчеты, но управляется “человеческим” запросом в чат.

## 9) Что обсудить, чтобы не уйти в бесконечность

Чтобы “комплексный анализ” был полезным, а не бесконечным, нужно заранее выбрать:

- primary outcome(ы) и 3-5 ключевых экспозиций,
- какой “уровень глубины” нужен (Basic / Standard / Deep),
- publication vs exploratory,
- какие ограничения по времени/ресурсам (deep mining может быть дорогим).

Если это зафиксировать, Gemini сможет предлагать богатый, но не бесконтрольный план, и система сможет делать воспроизводимый отчет с фиксированным N.
